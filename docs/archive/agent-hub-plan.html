Program plan · agentLedger

Building the Agent Hub

One app RE/MAX Jerusalem agents open for everything — their standing (owed / owing, has the client paid, has Ariyel paid me), receipt uploads, deal notes, new deals via the summary-of-terms form, and adding a property. agentLedger is the base; sikkumPigisha's wizard moves in and it's retired. Monday stays in two-way sync as a migration bridge, then it's archived.

Status Phase 0 · deploying Owner Levi Backup admin Ariyel Date 2026-09-03
01

Why one app

agentLedger and sikkumPigisha are ~60% the same code — Next 15 / App Router / Tailwind / shadcn, the same OTP → Daf Kesher → JWT auth, one Monday token, one WhatsApp template, one Redis account, one Green Invoice account. They independently carry near-identical auth/, monday/client.ts, commission.ts, waba/client.ts, redis.ts, and the UI primitives.

agentLedger has the DynamoDB layer, the four-role permission system, and the ledger. sikkumPigisha is single-role and form-only. So the wizard moves into agentLedger and sikkumPigisha is retired. Design polish is deliberately deferred — functionality first.

02

Decisions locked

Monday

Two-way sync as a migration bridge

DynamoDB is the source of truth from Phase 1. Monday mirrors both directions so the secretary, Ariyel, and the Make PDF scenario keep working — then the boards are archived within months. Daf Kesher (identity) stays.

Client signing

The hub is not a signing platform

The three external signing programs stay. The hub receives emailed copies of signed forms (haskama / biladiut / buyer representation), Claude-parses them into a draft record, Levi confirms, and it's matched to a property or deal.

Pipeline

Linked entities with propagation rules

Signed Contract ⇄ Property ⇄ Offer ⇄ Deal — each its own record and its own status, cross-linked. Rules propagate both ways: offer accepted → property "In Negotiation"; deal signed → property "Signed"; deal cancelled → property "Active".

Income

Green Invoice is the source of truth

Receipts (חשבונית מס / קבלה) are made on the Green Invoice website. A webhook tells the hub; it resolves the receipt to its חשבון עסקה (300), to the deal, creates the income row, and auto-posts the agent's commission. Scheduled poll as a fallback; manual PDF upload as a last resort.

Agent expenses

Billed via a 300, cleared by webhook

Expense rows are added — recurring ones automatically, others by hand. The hub then sends the agent a חשבון עסקה via the GI API; Levi charges their card in GI; the webhook marks those expenses paid (payment_by_agent). Ariyel always pays agents their full commission — expenses are settled separately.

Ledger amounts

Every entry carries both VAT figures

amount (VAT-inclusive — the cash figure, drives the daily-report balance) and amountExVat (pre-VAT — what the agent earns, what commission tiers accumulate). Already built.

Deal notes

Append-only timestamped log

Every deal — potential or signed — has a running thread. Each note carries its author and time; nothing overwrites. Agents write on their own deals, team leaders on their team's, managers on any.

Deferred

Contact layer, in-app PDF, WhatsApp control

Start with the Signed Contract as the client unit (dedup into a Contact entity later). Keep the Make.com PDF during the bridge; rebuild it in-app at Monday retirement. Managing the hub by WhatsApp command is a later layer — which is why every operation is written as a callable service now.

03

The pipeline

Sign client (haskama / biladiut) → for a seller, the property is listed and the secretary publishes it; for a buyer, an offer (הצעת מחיר) is made and accepted → the agent fills the summary of terms (prefilled from the offer + property + signed contract) → potential deal → Levi marks it signed (due) → חשבון עסקה → client pays → חשבונית מס / קבלה → income + auto-commission → agent sends their חשבונית מס → daily report → Ariyel pays → agent's קבלה.

Deals can be one-sided (we represent only the seller or only the buyer) — the other side is recorded by name only, no chase for their details.

04

Cross-cutting

Principles

  • Service layer — every business operation is a plain function in lib/services/*; the web forms and a future WhatsApp bot are thin callers
  • DynamoDB is the source of truth from Phase 1
  • Mirror writes never block the user — dead-letter log + a manager "resync" action
  • Ariyel = admin (reports + full backup for Levi). Secretary tooling is later
  • Reuse, don't rebuild — agentLedger's shared code wins; sikkumPigisha's extra pieces move over

Moves from sikkumPigisha

  • The 18-step wizard → /deals/new/(wizard)/*
  • Claude doc-extraction + the upload step
  • Monday board libs — properties, clients, offers, deal-write
  • Matching — property-match, offer-match
  • Wizard infra — step routing, Redis drafts, validation
  • Party sub-forms — owners / buyers / lawyers / agents, commission

06

Phases

Ordered. Each phase ships on its own and leaves the app working.

PHASE 0Foundations & deploy

agentLedger becomes deployable, with room for the work. No UX change. Mostly done.

  • ✓ New Amplify app (Git-connected). ✓ amplify.yml — writes env vars into .env.production at build; Amplify SSR doesn't expose console env vars to the runtime otherwise. This was the deploy blocker.
  • ✓ lib/services/{deals,payments,ledger}.ts; actions are thin callers.
  • ✓ dynamo-client.ts uses the Amplify compute role at runtime, static keys locally.
  • ✓ scripts/create-tables.mjs — 6 new tables + agent-ledger-agent-account (renamed from -ledger-entries).
  • — Run the table script, attach the IAM compute role, fill real secret values, verify login. pushToDrive() stub → Phase 3.
Ships: agentLedger live at the Amplify URL, feature-identical to today.
PHASE 1Dual-write bridge

DynamoDB becomes the read source; Monday stays current both ways.

  • lib/sync/ — mirrorOut upserts a hub record to its Monday board (fire-and-forget, dead-letter, resync action).
  • mirrorIn — a scheduled poll pulls Monday changes back, so secretary / Ariyel edits reach the hub during the bridge.
  • Backfill (2026-forward) — generalise the Weiser import scripts for Red File, Signed Contracts, Properties, Offers.
  • Flip all hub reads to DynamoDB.
Ships: every read served from AWS; Monday mirrors both ways.
PHASE 2Merge the wizard

Deal intake lives in the hub. sikkumPigisha retired.

  • Move the wizard tree to /deals/new/(wizard)/*; rewire to the shared libs. Keep the Claude upload / pre-fill step.
  • Submit → services/createDeal → DynamoDB + mirror to Deals_Raw_Data (Make PDF keeps firing) + Red File.
  • Prefill from the linked accepted offer + property + signed contract.
  • Redirect sikkumPigisha's URL → /deals/new. Its users re-login once.
Ships: one app, one login. Second codebase gone.
PHASE 3Green Invoice income + expense engine

Income and expenses come from GI documents, not typed numbers.

  • Green Invoice production cutover.
  • חשבון עסקה (300) stays a button — for a deal, and (new) for an agent's expense batch. Each 300 recorded in gi-documents with its target.
  • /api/green-invoice/webhook — receipt → its 300 → target. Deal → income + auto-commission + advance lifecycle. Agent → mark expenses paid (payment_by_agent). Poll fallback.
  • Manual upload portal. Remove the free-text "log payment" field. Monthly recurring-expense job.
Ships: income and expenses can't drift from Green Invoice.
PHASE 4Pipeline entities + propagation

The linked pipeline agents and managers navigate and update.

  • Cross-link the entities; lib/services/pipeline.ts runs the propagation rules on both a hub write and a mirrored-in Monday change.
  • Signed-form email ingestion → Claude extract → draft record → Levi's review queue.
  • "Add / update property" form — prefill owner from the signed contract, Google Maps address, photo upload, mirror to Properties.
  • Deal notes thread (own / team / all). Offers created & accepted in the hub.
Ships: agents self-serve notes, properties, offers; pipeline status is live.
PHASE 5Daily report, standing, notifications

Replace the manual Excel tabs and the hand-sent handoffs.

  • Agent standing view — income − expenses = net, plus a per-deal payment-lifecycle strip.
  • /reports/daily?date= — standings, "to pay today", RE/MAX Israel receipts, bank snapshot. Ariyel gets a checklist view.
  • WhatsApp notifications for each handoff — offer accepted, payment received, agent invoice in, Ariyel paid, expense billed, exclusivity expiring.
Ships: the daily report and standings come out of the hub.
PHASE 6Monday retirement

One system of record.

  • Stop mirrorOut / mirrorIn. Archive Deals_Raw_Data, Red File, Properties, Signed Contracts, Offers, Referrals. Keep Daf Kesher.
  • Rebuild the summary-of-terms PDF in-app; drop the Make scenario.
  • Full pre-2026 backfill if wanted.
Ships: single system of record.
Later, noted: WhatsApp-first management (natural-language commands over the service layer) · a design pass on the hub and the summary-of-terms form · secretary ad-publishing tools · the deduplicated Contact layer · bank-CSV import feeding the cash-flow reconciliation · agent self-service "mark signed" with a fraud-control gate.
